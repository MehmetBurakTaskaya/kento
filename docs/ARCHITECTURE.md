# Architecture

Kento is a Tauri 2 app: a Rust core (`src-tauri/`) with its local engines (`src-tauri/engines/`) and a React + TypeScript page (`src/`) in one window per surface. This file describes the code as it stands; the plan is in [SPEC.md](SPEC.md) and the progress in [ROADMAP.md](ROADMAP.md).

## Engines (`src-tauri/engines`, crate `kento-engines`)

Every conversion and tool. Only `media/`, image metadata, `office/` and `web/` need something outside Kento (FFmpeg, ExifTool, LibreOffice, yt-dlp and Deno, downloaded on request or found on the computer); the rest runs as it is. The crate knows nothing about windows, settings or the queue: it gets claimed paths, options and a progress handle, and runs on a blocking thread. Its tests run without the app (`cargo test -p kento-engines`).

| Module | Role |
| --- | --- |
| `image/` | Image inputs to image outputs and PDF; AVIF decoding in pure Rust; HEIC through the system (WIC on Windows, ImageIO on macOS) |
| `pdf/` | PDF pages to images, text, Markdown and tables (XLSX) on the bundled PDFium; merge, split, edit and PDF from images on `lopdf` |
| `archive/` | ZIP, TAR, GZ, RAR (read only) and 7Z: conversion entry by entry, and extraction with path, link, count and size checks |
| `text.rs`, `subtitle.rs`, `sheet.rs` | TXT, MD and HTML; SRT and VTT; CSV, TSV, XLS, XLSX and ODS without an office suite |
| `qr.rs`, `qr/`, `thumb.rs` | Reading QR codes in images and PDF pages, and making them as PNG or SVG; small previews |
| `recipe.rs` | Recipes: the model shared by the wheel, folder automation and the command line, a plan checked before anything runs, and the runner that chains the steps through temporary files |
| `bgremove/` | Background removal: ONNX Runtime loaded at run time with the BEN2 Base model, the mask laid into the picture's alpha |
| `ocr/` | Extract text with the system's own recogniser: Windows.Media.Ocr and Apple's Vision |
| `media/` | Video and audio through FFmpeg and ffprobe: conversions, the 13 media tools, probing, proxy previews, waveform peaks and frames, and HEIC where the system cannot read it |
| `image/tools/` | The six image editors (edit, crop, mark up, frame, collage, redact): one code path for the live preview at any scale and the full-size result |
| `compress.rs` | Compress: one entry that hands images to `image/compress.rs`, video and audio to `media/compress.rs` and PDF to `pdf/compress.rs` |
| `metadata/` | Metadata: images through ExifTool, PDF through lopdf, video and audio through ffprobe and FFmpeg (tags and chapters) |
| `office/` | Documents, spreadsheets and presentations through LibreOffice in headless mode, for the routes no engine inside Kento does, with the steps around it in Kento's own engines: Markdown, text, text clippings and EPUB in, Markdown out, slides as pictures, PDF pages as slides, Apple package documents |
| `web/` | Web media download through yt-dlp: asking what a link holds (site, kind, title, the simplified quality list, the pictures of a photo post) and downloading one choice, with progress, into the job's folder |
| `process.rs` | Running the external tools: no console window, cancelling, and ending a tool together with what it started (a job object on Windows, a process group elsewhere) |

## Rust core (`src-tauri/src`)

| Module | Role |
| --- | --- |
| `lib.rs` | Starts the app: plugins, state, tray, the main window; keeps running in the tray when the window closes |
| `catalog/` | Every format, conversion route, tool and file action (SPEC 5.1). `export.rs` writes `docs/FORMATS.md` and `website-kit/catalog.json` (`npm run catalog:export`; CI checks they are current) |
| `jobs/` | The job queue: light jobs side by side up to a limit, heavy jobs one at a time, cancellation, pausing, progress events. `naming.rs`: output names and safe writing for files and folders; `engine.rs`: a job that runs an engine under a claimed name with its own scratch folder |
| `work.rs`, `tools.rs` | The Convert and Tools wheels' contents for a selection, conversions (one job per file) and the core tools; slices that need a missing tool open the setup |
| `toolchain/` | The optional tools (SPEC 4.2): finding them (a path set in Settings, PATH and the usual install folders, Kento's own folder), the pinned downloads of `toolchain.lock.json`, resumable downloading, the SHA-256 check and unpacking only the named binaries and folders (LibreOffice: an administrative install of the MSI on Windows, a copy out of the disk image on macOS) |
| `media.rs` | The media commands: probing, previews (proxy files in the temp folder), waveform peaks, frames and the media tools' jobs |
| `images.rs`, `compress.rs`, `metadata.rs` | The image editors' size and preview commands (with a small cache of decoded pictures) and their jobs; Compress, one job per file; Metadata's read and its job |
| `files.rs`, `library.rs` | Choosing and pasting files, previews, and the Library (`library.json`, the last 50 outputs) |
| `settings.rs` | Settings as JSON in the data folder; broken files are kept aside, values are clamped |
| `i18n.rs` | The languages, system-language matching, and the strings Rust shows (tray menu) |
| `shelf/` | Kento's own shelf (SPEC 5.8): references, history, "keep a copy", in `shelf.json` |
| `overlay/` | The windows over other apps: the floating wheel (`wheel.rs`: the drag session and click mode), the shelf window and the result card. They hide by moving off screen |
| `platform/` | What the system provides: drags seen anywhere and the modifiers held, the Explorer or Finder selection, sharing, a terminal, Send To and the context menu; `windows/` and `macos/` |
| `actions.rs`, `shortcut.rs` | The file actions wheel; the selection and download shortcuts |
| `web.rs`, `drops.rs` | Web downloads: probing a link, the download jobs, the default folder, picture previews fetched for the dialog; what a drag over a window carries (files or one link), sent to the page as one event |
| `paths.rs`, `logging.rs` | The data folder (`%LOCALAPPDATA%\Kento`, `~/Library/Application Support/Kento`), temp clean-up, rolling logs |
| `window.rs`, `tray.rs` | The main window (built on demand, Mica on Windows 11) and the tray or menu bar icon |
| `commands.rs` | What the page may call; links and folders are decided in Rust, never taken from the page as they are |
| `recipes.rs`, `automation/` | Recipes in `recipes.json` and their jobs; folder automation: rules, the watcher (`notify`), the wait for finished writes, loop protection, pausing and the activity log |
| `layouts/` | Window layouts: the eight placements, their shortcuts, the Window ring and the per-system code (DWM frame bounds on Windows, Accessibility on macOS) |
| `bgremove.rs`, `ocr.rs` | The background-removal and text-extraction commands and jobs |
| `cli/`, `bin/kento_cli.rs` | The command line: arguments, console handling, lists from the catalog, and jobs run one at a time with the app's own naming and engines |
| `smoke.rs` | `kento --smoke-test`: a hidden run that checks the parts that exist and writes `smoke-test.json` |

## Page (`src`)

| Folder | Role |
| --- | --- |
| `app/` | The window's shell (navigation rail) and its pages: Home, Library, Settings (with the tools' state); file input (drop, Ctrl+O, Ctrl+V), the wheel's host and the tool setup |
| `wheel/` | The steel safe-dial wheel: drawing, hit-testing, keyboard, motion and synthesized sounds |
| `automation/` | The Automation page: rules, the recipes editor and the activity log |
| `web/` | The download dialog: choices from what the link holds, the quality list, the picture picker, the first-use notice |
| `tools/` | The panels of the tools that need choices: Merge PDFs, Split PDF, Edit PDF, PDF from images, Read QR codes, Compress, Metadata |
| `editors/` | The media editors: one player, timeline and waveform shared by the video and audio tools, with the keys of SPEC 5.6; `editors/image/`: the image editors, a zoomable stage with the engine's preview, mark up drawn as SVG with undo |
| `components/` | Icons, file previews, the dialog and the cards in the corner |
| `i18n/` | i18next with ICU messages from `/locales`, right-to-left switching, the pseudo-languages `en-XA` and `ar-XB`, and language-aware formatting and search |
| `theme/` | Themes as plug-ins (`registry.ts`); the default steel theme (`steel.ts`, values from `design/DESIGN.md`) |
| `state/` | The page's store (Zustand) |
| `ipc.ts` | The only door to the core; in a plain browser it answers from memory, so `npm run dev` and the screenshot script work without the app |

Strings live in `/locales/*.json` and are shared by both sides. Layout uses CSS logical properties only, so right-to-left needs no separate rules.

## Decisions

1. **Own settings file instead of the store plugin.** A small, versioned JSON file with clamping and a kept-aside copy of a broken file is easier to test and to migrate.
2. **`tracing` for logs.** Rolling daily files, seven kept; the page logs through a command that shortens its text. No file contents are ever logged.
3. **The main window is destroyed on close and built again from the tray.** Kento waits in the tray with little memory, and Mica is applied once per window, never toggled by hiding and showing.
4. **Windows are built from their own thread.** WebView2 cannot finish setting up a webview while the main thread waits in a command or an event handler.
5. **Links and folders through Rust commands.** The page has only the `core:event:default` permission; there is no opener or file system access from the page.
6. **Pseudo-language codes `en-XA` and `ar-XB`.** i18next rewrites codes such as `qps-ploc` to `qps-Ploc`, so the private-use region codes known from Android are used. Development builds accept them as a setting.
7. **Plugins only when their phase needs them.** Phase 1 uses single instance, autostart, opener and dialog; the global shortcut, updater, deep links, clipboard and notifications arrive with their features.
8. **Engines in their own crate.** The heavy format libraries build and test without the webview, and the CLI (Phase 8) can use them as they are.
9. **PDFium ships inside Kento.** `npm run pdfium` fetches one pinned build of the pdfium-binaries project, checks its SHA-256 and puts it in `src-tauri/resources/pdfium` (not committed); the installer bundles it and the app loads it at start. Every PDFium call goes through one lock, because PDFium is not thread-safe.
10. **No assembler in the build.** AV1 decoding (`rav1d`) and encoding (`ravif`) run without their assembly code, so building needs no NASM; AVIF pictures are small, so the speed is enough.
11. **HEIC through the system.** Windows decodes HEIC with the HEIF Image Extensions through WIC and macOS with ImageIO; without them the job explains what to install.
12. **Unwinding panics in release builds.** A parser that panics on a malformed file ends that job with an error; Kento keeps running.
13. **Encrypted PDFs are refused,** also those with only an owner password, so Kento never drops a document's restrictions.
14. **RAR through UnRAR's test mode.** The library streams each entry to Kento and never writes files or links itself; extraction then applies Kento's own path and size checks.
15. **The clipboard is read only on paste.** Files come from the system clipboard (CF_HDROP on Windows, the pasteboard on macOS); text and images from the paste event. Imports go to the output folder, or Downloads/Kento.
16. **The page opens only what Kento wrote.** Opening and showing go through Library ids, so the page cannot launch arbitrary files.
17. **The floating wheel waits off screen.** Its window is defined in `tauri.conf.json`, visible from the start and parked at -20000, so WebView2 has registered it as a drop target before the first drag; showing it is a move to the pointer. It never takes the focus during a drag, which would break the source app's drag loop.
18. **Drags are seen by polling, not hooks.** A thread reads the button, the pointer and the modifiers (and the drag pasteboard on macOS): every 40 ms while the button is up, every 10 ms while it is down. No keyboard hook, no Accessibility or Input Monitoring permission.
19. **The drag tells what it carries.** The wheel learns what is dragged when the drag enters its window: files open the usual wheel, one web address opens the Download ring, anything else closes it silently. WebView2's own drop target reads only files, so on Windows Kento puts its own OLE drop target on the webview's windows (files, URL formats, Firefox's link format, a single link as text); on macOS a drag without files is read from the drag pasteboard. A web address wins over files, since browsers may add a temporary copy of a dragged picture. Because a drop ends the drag, a category of a mixed selection opens its ring when the pointer rests on it, and resting on the hub goes back.
20. **Explorer integration stays off until switched on.** Send To and the context menu write only under the user's profile (HKCU); Explorer may start Kento once per file, and launches within 400 ms join one wheel.
21. **Tools on the computer come first.** A path set in Settings, then PATH and the usual install folders (WinGet links, Homebrew), then Kento's own download. Each candidate is run once and must report a version Kento drives (FFmpeg 6, ExifTool 12, LibreOffice 7 or newer); anything else is ignored. LibreOffice answers through `soffice.com` on Windows (`soffice.exe` prints nothing) and with a throwaway profile, so the check never hands itself to a LibreOffice the user has open. A program is chosen in the system's file dialog, so the page can never name one for Kento to run.
22. **Only pinned files are downloaded.** `toolchain.lock.json` is built into the app with each file's URL (HTTPS), size and SHA-256. A download resumes with a Range request, is checked before anything is unpacked, and only the binaries and folders the lockfile names are taken out, under names Kento chooses (ExifTool's Windows program needs its `exiftool_files` folder, the Perl version its `lib` folder). Each version gets its own folder, so an update never touches a working install. LibreOffice cannot leave its program folder: its MSI is unpacked by an administrative install (`msiexec /a`, which registers nothing and needs no elevation) and its disk image is attached read-only while `LibreOffice.app` is copied out with `ditto`; the lockfile names the folder to keep (on Windows the whole image, which has no folder of its own, without the administrative copy of the package) and where `soffice` sits inside it.
23. **Native where a pinned build exists.** FFmpeg has no static Apple silicon build with fixed, checkable release files yet, so Apple silicon runs the Intel build through Rosetta 2, which macOS offers to install on first use; Deno and LibreOffice are pinned natively for both Mac kinds, and yt-dlp's macOS build is universal. A group installs only the tools it is missing, and a tool with a version of its own (yt-dlp, Deno) gets its own folder, so one can be replaced without touching the others.
24. **External tools run as separate processes.** Arguments go as arrays, paths are anchored so that FFmpeg never reads them as options or protocols, no console window opens on Windows, progress comes from `-progress`, and cancelling ends the process together with anything it started (on Windows through a job object, because package-manager shims start the real FFmpeg as a child). Builds without libvorbis or libopus, such as Homebrew's, use FFmpeg's own encoders for those formats. Kento's code and FFmpeg's GPL code never link. ExifTool and LibreOffice run the same way (`process.rs`).
25. **Previews play the original when the webview can.** Otherwise FFmpeg writes a small H.264 proxy into the temp folder (named by the source's path, size and time, reused until it changes). The asset protocol starts with an empty scope; each previewed file or proxy is allowed one by one. Exports always read the original.
26. **HEIC falls back to FFmpeg.** Where the system cannot decode HEIC (Windows without the HEIF Image Extensions), FFmpeg 7.1 or newer turns the photo into PNG in memory, tiles and turn included; an older FFmpeg would give one tile as the photo, so it is not used for this.
27. **Previews come from the engine.** The image editors ask for a PNG of the tool applied to a scaled-down copy; the engine runs the same steps as for the result, with every coordinate scaled, so what the editor shows is what gets written. Decoded copies are kept for the next request, so sliders redraw quickly. The page draws only what follows the pointer (crop and redact areas, marks).
28. **Mark up is SVG on both sides.** The page draws the marks as SVG over the picture; the engine builds the same SVG from the same marks, with the same rules (strokes, arrow heads, a group opacity per mark, text in the system's sans-serif) and renders it with resvg. Marks are data, never markup from the page, so nothing can point the renderer at a file.
29. **Compress keeps the format and never writes a larger file.** Pictures search the encoder quality and then the size; video and audio get a bit rate from the duration, two passes and smaller frame sizes when bits run short; PDF stores its pictures again as smaller JPEGs. A result that is not smaller, or not under the target, is deleted and the job says so.
30. **ExifTool through an argument file.** Every argument goes in a UTF-8 file read from standard input with `-charset filename=utf8`, so Turkish and emoji paths and values survive the Windows command line; ExifTool writes a new file in the job's folder, which then moves to its name. PDF metadata is rewritten in full by lopdf (ExifTool's PDF edits are incremental and can be undone), and video and audio tags by FFmpeg with the streams copied.
31. **LibreOffice works on copies, in its own profile.** Each job copies its input into its scratch folder under a plain ASCII name, so LibreOffice never sees the user's file names or folders, and copies the result to the claimed name. The app keeps one LibreOffice running headless with Kento's profile (kept in the data folder) and a local UNO pipe; each job hands its document over with a small script of Kento's run by LibreOffice's own Python, so only the first job waits for LibreOffice to start (about 0.35 s per document afterwards instead of several seconds). The kept instance ends after five idle minutes, on a crash, a cancel or a timeout, when another process waits for the profile, and with Kento; without a bundled Python, or when the pipe does not answer, a job runs `soffice --convert-to` once as before. A file lock holds the profile for one LibreOffice at a time, and the queue runs office jobs one at a time in its heavy lane. A run counts only when it wrote a non-empty file, since LibreOffice can end without an error after failing to load a document; a crash report in the profile ends a run at once and it gets one more try. The profile keeps LibreOffice's own interface in English: with a Turkish interface, its translations ask the C++ library for the locale Windows names "Turkish_Türkiye", which a process running in UTF-8 cannot open, and LibreOffice crashed on every document. 
32. **Office documents stay offline and inert.** Before every run the profile is set so that documents cannot run macros, linked content from untrusted documents is blocked, links are never updated and formulas never recalculated on load, and no crash report or update check goes out. HTML, Markdown made into HTML and EPUB chapters lose every reference that would load something from elsewhere before LibreOffice sees them; pictures next to the document are embedded, remote ones dropped. Links stay as links in the result.
33. **Kento does the steps LibreOffice cannot.** LibreOffice has no EPUB or Markdown import and writes slides as one picture, so Kento reads EPUB itself, turns Markdown into HTML and HTML back into Markdown, renders slides through a PDF with PDFium, and builds a flat ODP with one picture per page for PDF to PowerPoint. PDF to XLSX needs no LibreOffice at all: the PDF engine reads the tables from where the text sits on each page.
34. **Apple package documents count as files.** A PAGES, NUMBERS, KEY or RTFD document can be a folder that Finder shows as one file; Kento takes such a folder as a document of its format (an iWork package is zipped for LibreOffice, RTFD gives its `TXT.rtf`). Every other folder stays a folder.
35. **yt-dlp runs shut off from everything but the link.** It ignores the user's yt-dlp configuration and plugins, never updates itself, never reads or writes cookies, fetches no remote scripts, and uses Kento's Deno as its only JavaScript runtime and Kento's FFmpeg; Deno's own update check is off. It writes only into the job's folder; finished files then move to the chosen folder under names from the title. Live streams, whole channels, profiles and playlists are refused from the probe, and again if a download turns out to be one.
36. **yt-dlp updates on its own.** "Update yt-dlp" in Settings asks GitHub for the latest release only when clicked, downloads the program and that release's `SHA2-256SUMS`, checks the hash, and uses the new copy only once it answers `--version` with the release's own version; the pinned copy stays as a fallback. A yt-dlp installed elsewhere is updated where it was installed.
37. **The page never loads remote content.** The strict CSP stays: the pictures of a photo post are fetched for the dialog by the core (HTTPS, image types only, a size limit) and handed to the page as data. A link pasted, dropped or read from the clipboard by Ctrl+Shift+D is checked to be one http or https address in the core, and the clipboard is read only when the shortcut is pressed.
38. **One recipe runner for every entry.** Recipes live in the engines, so the wheel's Favorites, folder automation and the command line run the very same steps. A plan is made before anything runs: it knows each step's format and refuses a step that does not fit (cropping a video) before any file is touched.
39. **Automation never chases its own tail.** A file counts as finished once its size has held for two seconds. A rule never takes a file in its own output folder, every output Kento wrote is remembered for an hour, a file is taken once until it changes, and hidden, partial and lock files are skipped. Pausing stops watching, so files that land while paused are not handled later. The activity log keeps names and outcomes, never contents.
40. **Window layouts stay out of Snap's way.** No shortcut uses the Windows key and Kento never snaps; it places windows with `SetWindowPos` by the frame DWM draws, so the visible edges of two halves meet. Ctrl+Alt is combined only with keys that type nothing, since some keyboards read Ctrl+Alt as AltGr. Windows of elevated apps are left alone quietly. The feature is off by default; on macOS the Accessibility permission is asked for only when it is switched on, after Kento has said why.
41. **Background removal runs a model on the computer.** ONNX Runtime is loaded at run time from Kento's own folder (never from PATH or a chosen path), with its telemetry off; the model and the library are resources Kento loads, not programs it runs. A loaded session is dropped after a minute without use, and jobs run one at a time in the heavy lane. Only permissively licensed models are used.
42. **Text is read by the system.** Extract text uses Windows.Media.Ocr and Apple's Vision, so no model is downloaded; the language is the interface's when the system reads it, and a missing language is named with where to add it. PDF pages are drawn by PDFium first.
43. **Burned-in subtitles never put a path in a filter.** The subtitle file is read by Kento, written again as UTF-8 SRT into the job's folder beside a copy of the system's font, and FFmpeg runs in that folder, so no drive letter or special character reaches the `subtitles` filter. An FFmpeg without libass is recognised and explained.
44. **The command line is a program of its own.** A console binary beside the app, so terminals wait for it, pipes and exit codes work and Ctrl+C cancels the job and removes its partial output; it never starts the window, the tray or the single-instance hand-off. It finds tools the way the app does, but only the groups a command needs, and ignores the app's fixed output folder so a script's result never depends on a setting. The command line uses a LibreOffice profile of its own and one LibreOffice run per job, so a script never waits for the app's kept LibreOffice and never ends it.
45. **Rings of choices are one mechanism.** A slice may carry variants, a default and a subtitle; categories of a mixed selection, the Favorites recipes and every ring of choices (PDF, quality, presets, recent folders) are built the same way in `src/app/slices.ts` and `variants.ts`, and both the main window's wheel and the floating wheel only carry out the plan a choice returns. Choices that tune a conversion travel as a preset the core checks against the route; recent Copy and Move folders are kept by the core, which refuses any other folder from the page. Going in and back is animated with transforms and opacity only, so a drop during the animation lands on the slice under the pointer.
46. **Releases and updates follow Panopin.** A `v*` tag builds a draft release whose files keep fixed names (`Kento-Windows-x64-Setup.exe`, `Kento-Windows-x64-Update.exe`, `Kento-Windows-x64-Portable.zip`, `Kento-macOS-Universal.dmg`, `Kento-macOS-Universal.app.tar.gz`, `latest.json`, `SHA256SUMS.txt`); publishing it hides the older releases as drafts instead of deleting them, so nothing is lost and download counts stay. `latest.json` uses github.com download addresses, never API ones (60 unauthenticated requests an hour), and has one signed entry per way Kento is installed: `windows-x86_64` (the installer, run quietly), `windows-x86_64-portable` (the ZIP) and `darwin-aarch64`/`darwin-x86_64` (the universal app archive). A copy with Tauri's `uninstall.exe` beside it is installed; one without is portable; a development run never installs. The update key was made with `tauri signer generate` and has no password. Every Mac build is signed with one self-signed certificate, named in `src-tauri/macos-requirement.txt`, so macOS matches each update to the permissions given before.

## Checks

`npm test`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run check:i18n`, `npm run check:spdx`, `npm run check:licenses`, `npm run check:third-party`, `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test --workspace` (PDF tests need the fetched PDFium, media tests FFmpeg, image metadata tests ExifTool, office tests LibreOffice, web tests yt-dlp and Deno against a local server, never the internet; CI installs them all and sets `KENTO_REQUIRE_FFMPEG=1`, `KENTO_REQUIRE_EXIFTOOL=1`, `KENTO_REQUIRE_SOFFICE=1` `KENTO_REQUIRE_YTDLP=1` and, with the pinned runtime and model, `KENTO_REQUIRE_BGREMOVE=1`), the catalog check and `cargo deny` run in CI on Windows and macOS (`.github/workflows/ci.yml`), followed by a release build, the smoke test and a run of the release command line. A second workflow (`.github/workflows/toolchain.yml`) installs every pinned tool build for real, as the app does on request, by hand and whenever the lockfile or the install code changes. `npm run shots` takes screenshots of the pages in English, Turkish and both pseudo-languages.
